# LLM administration and estimated usage cost

The LLM tab displays the saved primary and ordered fallback routes as cards, with a configured-chain summary. These are database configurations, **not** proof of provider or worker health. Editing a card creates a new version; it does not mutate an active or pinned version. To change a fallback, save its new version as a draft, then select that draft in a new primary version's fallback chain, explicitly approve every destination, and activate the new primary. Reordering/deleting an entry from the editor affects the new chain only. Activation is audited; in-flight and recovered operations retain their original configuration.

The Admin can enter USD prices per **one million** input/output tokens for each version. Blank means unknown, not free; `0` explicitly means free. Prices are manually entered, not fetched from provider catalogs. They are copied into the public operation snapshot; a changed price requires a new version and never retroactively changes prior attempts. A saved compatible key can be reused only for the same canonical Base URL and an explicitly selected source version (or the current active version); a new URL requires a new key. Keys remain encrypted at rest and are not returned or included in snapshots. Connection tests use a minimal synthetic prompt, can incur a provider charge, and are not included in this estimate.

## Meaning and limits of the total

- Estimated USD = `(input_tokens × input_price + output_tokens × output_price) / 1,000,000` for each observed LLM HTTP attempt with both valid integer token counts and both configured prices. The price belongs to the route actually attempted, including a fallback. Known zero is included; unknown is never silently counted as free. If a provider supplies a model name that differs from the configured model, the attempt is unpriced rather than using a potentially wrong rate.
- A separate, privacy-minimized `app_private.llm_usage_attempts` row is recorded per observed LLM network attempt, including retries, invalid model output and failures where observable. It stores no prompt, CV/JD, credential or applicant identifier. Failed requests, timeouts, missing/invalid token usage, missing prices and model mismatches are shown as unpriced. Attempt records and their price snapshots are best effort: process crashes, telemetry/database failures, unreported provider usage and older code can leave gaps. The counter cannot detect attempts that were never recorded.
- The all-time total starts with observations after deployment; no historical usage is reconstructed. The sidebar displays up to five most recent config groups while the total covers all stored rows. Test connections, BGE embeddings, reranker calls, other AI services, taxes, discounts, cache pricing, billing tiers and currency conversion are excluded. Some providers count token categories differently. **This is an incomplete operational estimate, not a bill, budget guard, or guaranteed lower bound**; reconcile against provider invoices.
- The table is Admin-only through the API, with backend service-role SELECT/INSERT and no direct anon/authenticated access. It currently has no automated retention/purge schedule; operators must account for its storage growth and set an approved retention policy before production.

## Rollout

`00021_llm_prices_and_usage.sql` is required before deploying this code; existing configs get NULL prices and no data is backfilled. For databases other than the designated test project, obtain the appropriate authorization and backup/restore decision. Drain HRA processes and avoid mixed-version workers before deployment. The deploy script detects migration changes but never applies them. On test project `myrymlqdbyqmpynesiwk`, the operator authorized automatic migrations; `00021` was applied as Supabase version `20261113031442`. No separate backup was created or independently verified for this application. Postflight showed zero usage rows, zero configured prices, one active LLM, BGE ON, LTR OFF and reranker OFF. Code deployment and worker behavior have not been verified. Keep unrelated Narrative processes untouched. No provider key or price is configured automatically.

Synthetic tests use mocked HTTP and a disposable PostgreSQL only. They verify price validation, missing usage, zero, retry observations, role permissions, endpoint-bound key reuse and immutable version pricing; they do not validate a real provider's billing, UI in a production browser, or the accuracy/completeness of invoices.


## Dashboard vận hành (migration 00022)

Admin → Vận hành LLM hiển thị 7/30/90 ngày theo thời điểm hiện tại, tổng hợp toàn khoảng và phân trang nhật ký tối đa 100 lượt/trang. Đồ thị theo ngày UTC; chi phí chỉ gồm lượt đủ giá/token và có đếm lượt không tính được. Lượt thử HTTP bao gồm retry/fallback, không phải tác vụ thành công; HTTP 2xx không đảm bảo JSON hay nghiệp vụ hợp lệ. Các bản ghi cũ có thể coi lỗi parse JSON là HTTP failure. Độ trễ mới đo đến khi HTTP trả lời hoặc lỗi, không tính parse; dữ liệu cũ không backfill. Tên model trả về chỉ lưu khi khớp tên yêu cầu (hoặc hậu tố ngày YYYY-MM-DD), có thể không được ghi. Bản ghi là best-effort và không bao gồm kiểm tra kết nối, BGE hay reranker; chi phí không phải hóa đơn, số tiền thiếu không là zero. Không có retention/purge tự động. Chỉ admin qua backend được đọc, không ghi prompt, phản hồi, CV/JD hoặc khóa.

Áp migration trước khi deploy backend/worker mới: metadata mới cần schema 00022; deploy backend trước migration sẽ khiến ghi telemetry thất bại (fail-open) và dashboard không tải. Cột mới nullable; backend cũ tiếp tục ghi sau migration. Index tạo thông thường có thể khóa ghi ngắn; migration đặt lock timeout 5 giây. Trước khi chạy kiểm tra kích thước bảng, tải/transaction và kế hoạch khôi phục phù hợp; không áp chỉ vì thấy test pass.

Supabase test `myrymlqdbyqmpynesiwk`: 00022 đã áp version `20261113034246`; preflight 0 attempts, 24,576 bytes, không thấy transaction quá 1 phút; hậu kiểm bốn cột nullable, index, quyền và BGE ON/LTR OFF. Không tạo hoặc xác minh bản sao lưu riêng. Không deploy ứng dụng hay bật Langfuse bằng migration.
